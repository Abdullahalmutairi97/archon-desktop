# Security model

The backend requires a configured single-owner bearer credential and a loopback listener. Missing credentials fail before database creation. Anonymous access is allowed only when an isolated fixture explicitly sets `fixture_mode=True`; `/api/health` remains minimal anonymous liveness in ordinary operation. HTTP and terminal WebSocket authentication use the same constant-time comparison, and WebSocket authentication has a bounded timeout before any terminal opens.

Generate new credentials with the [operator setup helper](operator-setup.md): at least 256 random bits, written once to a mode-0600 file in a private external directory. Supply every configured scratch/account and registered project root so the helper can reject workspace destinations. The server consumes exported configuration; it does not implicitly read a repository `.env`. Keep provider credentials, SSH keys and backup encryption material out of API responses, Git and logs.

Direct plaintext tailnet/public/private-interface listeners are rejected. Remote operation requires a separately managed private HTTPS proxy forwarding to loopback, bearer authentication and an explicit valid HTTPS configuration. This source validates configuration only: it does not deploy or verify private ingress, TLS, certificate trust or network reachability. Uvicorn does not trust forwarded headers by default.

Anything running as the service account is inside the trust boundary. The server clears its dumpable flag at startup and logs a warning when a host refuses that call, so `/proc/<server>/environ` is no longer readable by other same-uid processes; but the broker ledger, the local pairing socket and any provider origin remain reachable by such a process. A same-uid writer can add its own reference to the broker ledger and make the broker send the stored credential to an origin of its choosing, which was reproduced on this host. Do not describe the broker as preventing shell or direct-HTTP access: [same-uid exposure evidence](releases/p5-same-uid-exposure-evidence.md) records exactly what is and is not prevented.

Secret-backed actions go through an isolated credential-holding broker instead of handing a credential to a caller. A credential value exists only in the server process (from the service manager's external environment file) and is addressed by an operator-registered reference; the broker resolves the value itself, performs the upstream HTTPS request over an allowlisted request shape with no redirect following, and returns only a bounded, redacted result. Each action needs a short-lived single-use grant bound to the principal, the tool name, a digest of the exact arguments, the attempt id, the workspace identity plus its current generation and the ledger epoch; a grant is consumed before the upstream call starts, so an ambiguous failure is never retried silently with the same grant, and revoking a reference bumps the epoch to invalidate every outstanding grant. Reference metadata, provider auth states (never values) and a bounded decision audit live in a private 0600 document owned by this user, and the surfaces that read them demand the owner credential. This is a capability boundary inside the server process; it does not contain a process that already shares the service account's file access, and no provider or MCP adapter consumes it yet.

Runtime children can additionally be confined: with `ARCHON_DESKTOP_RUNTIME_ISOLATION_PROFILE=workspace-only` the Prime and Pi task process starts inside bubblewrap with a read-only host and only its checkout, session directory and a private temp directory writable. Every confined view (this one and a service's `filesystemIsolation: "workspace-only"`) runs in its own PID namespace and replaces `/run`, `/tmp`, `/var/tmp`, `/dev` and the account's home with private empty directories, because a read-only mount does not stop `connect()` on a unix socket: without that, `systemd-run --user`, the docker socket and editor sockets escaped the sandbox. Only the confined program's install tree is shown back read-only, and a runtime sees its own native home through a discarded write layer. The mechanics are probe-verified before a run and the run is refused when they cannot be enforced; runtime compatibility inside that profile has not been qualified with a real provider turn, so it is off by default. The network namespace stays shared unless a service declares `networkIsolation: "isolated"`. New child processes receive explicit allowlists for their purpose. Essentials such as PATH, HOME, locale and selected XDG paths survive; coordinator and Telegram tokens, arbitrary provider keys, ambient Python/Node injection settings and shell-startup variables do not. No ambient provider credentials are currently registered. Hermes and voice receive narrowly scoped server-owned overrides. Existing native processes and tmux servers may retain their old environments. All native agents still share their OS account's file access; environment filtering is not a process or filesystem sandbox.

Filesystem APIs canonicalize configured roots and block traversal and secret-like names. HTTP write paths (file save/create, workspace service start, the code-server handoff and workspace terminal creation) require an exclusive, expiring per-workspace write lease: the request takes the lease for the identity its credential carries and a live lease held by another writer is refused before anything is written, so moving write access needs an explicit handover. That fences API writers against each other; native processes, kernels, debuggers and detached tmux children are not yet fenced. Workspace service preview tickets are short-lived capabilities for one binding: every proxied request and open WebSocket re-checks the live workspace generation, service and process, and a definition, start, stop or removal drops the tickets for that service. The IDE handoff binds code-server to a unix socket in the server's private state root (socket mode `0600` inside a `0700` directory) instead of a loopback TCP port, so the listener is reachable only by this account and only through the preview gateway; code-server still runs with `--auth none`, so a process running as the same account stays inside the trust boundary. SQL uses parameterized statements and subprocesses use argument arrays. Trusted execution may still invoke external tools or modify files with the service account's authority. Destructive operational APIs retain confirmation and audit requirements.

The maintained desktop source/build work in P2 must establish context isolation, a minimal validated preload bridge, disabled renderer Node integration and protected or memory-only connection credentials. Historical source intent and fixture checks do not establish those properties in the missing frozen v0.3.0 ASAR or an installed client. Native credential storage and onboarding remain qualification gates.

Authenticated readiness distinguishes storage/worker/executable dispatch eligibility from provider credentials, successful execution and native conformance. It reports those verification flags as false until separate evidence exists. Worker heartbeats are process-local event-loop observations, not proof of agent progress or exactly-once effects.
